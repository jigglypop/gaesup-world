# Engineering Principles

속도가 기본값이다. 프로세스는 architecture boundary를 바꿀 때만 지불하는 비용이다.

## 투 트랙

- **Fast track (기본)**: 버그 수정, 도메인 내부 변경, 성능 개선, 리팩터링. plan 문서 없이 바로 구현한다. 검증은 최소 사다리(아래)만.
- **Epoch track**: architecture boundary·public API 계약·source of truth를 바꾸는 변경만. 이때만 `.codex/plans/active/` plan과 HARNESS.md 기록을 요구한다.

애매하면 fast track으로 시작하고, boundary를 건드리게 되는 순간 plan을 쓴다.

## 코드량

- 모든 diff는 net LOC 최소화를 목표로 한다. 삭제가 추가보다 낫다.
- 작업 범위 안의 죽은 코드·미사용 export·중복 구현은 발견 즉시 제거한다.
- 새 파일·새 클래스·새 스토어보다 기존 파일 확장을 먼저 검토한다.

## DRY

- 새 유틸이나 추상화를 쓰기 전에 `src/core/boilerplate/`와 `src/core/utils/`를 먼저 검색한다. 이미 있는 것을 다시 만들지 않는다.
- rule of three: 같은 패턴이 세 번 반복되기 전에는 추상화하지 않는다. 두 번째 중복은 그냥 둔다.
- 복사-수정으로 만든 파일이 원본과 80% 같으면 합친다.

## KISS

- 요구된 것을 최단 경로로 구현한다. 기존 도메인 템플릿(bridge 3메서드, plugin 등록)은 따르되 새 계층·새 패턴·새 데코레이터를 발명하지 않는다.
- 조건문으로 충분한 곳에 전략 객체·레지스트리·이벤트를 쓰지 않는다.
- 간접 참조(indirection)는 그 자체가 비용이다. 한 번만 호출되는 래퍼 함수를 만들지 않는다.

## YAGNI

- 미래 대비 옵션, 설정 플래그, 제네릭 파라미터, 확장 포인트를 추가하지 않는다. 두 번째 사용처가 실제로 나타날 때 추가한다.
- "나중에 필요할 수도 있는" 타입·인터페이스·훅을 미리 export하지 않는다. 공개 API 표면은 그 자체가 유지비다.

## 최소 검증 사다리

1. 변경 도메인 테스트 + 빌드 타입체크 — 항상.
2. publicApi/packageExports 가드 — 공개 API·subpath를 건드렸을 때만.
3. 전체 스위트 — 브리지·커널·스토어 조합 등 횡단 변경일 때만.

전체 lint, 전체 스위트를 습관적으로 돌리지 않는다. 실행한 것만 보고한다.
